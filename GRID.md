# Helm — Grid System

## What This Is

Helm is a personal dashboard app built around modular widgets. The long-term goal is a user-owned space where components can be added, arranged, and eventually generated by an agent. Right now, we are focused exclusively on one thing: **getting the custom component grid right**.

Everything else — widgets, persistence, extensibility — comes after.

---

## The Grid Model

The layout is a **binary tree** of nodes. There are exactly two node types:

```
LeafNode  — a slot that holds one component
SplitNode — divides space between two children (H or V) with a ratio (0–1)
```

Every visible slot is a `LeafNode`. Every division of space is a `SplitNode`. The tree is always full — no empty branches, no gaps, no overlaps.

**Example tree for a 3-slot layout:**

```
SplitNode (horizontal, ratio 0.5)
├── LeafNode (left slot)
└── SplitNode (vertical, ratio 0.5)
    ├── LeafNode (top-right slot)
    └── LeafNode (bottom-right slot)
```

The `ratio` on a `SplitNode` is a float from 0 to 1, representing the fraction of space given to the first child. It is clamped to [0.1, 0.9] to keep slots visible.

## Operations

All state lives in `useLayout()`. The tree is always replaced with a new immutable copy.

**split(id, direction)** — Converts a `LeafNode` into a `SplitNode`. The original leaf becomes the first child; a new empty leaf becomes the second. Starts at 50/50.

**remove(id)** — Removes a leaf. The parent `SplitNode` is replaced by the sibling. If the last leaf is removed, a new empty one is created as a safety fallback.

**resize(path, delta, containerSize)** — Adjusts the `ratio` of a `SplitNode` found at `path` (a breadcrumb trail like `['first', 'second']`). Converts pixel delta to ratio delta, clamps to [0.1, 0.9].

**swap(idA, idB)** — Swaps the `componentId` values between two leaves. The slots themselves stay in place; only their contents exchange.

---

## Rendering

`LayoutEngine` is a recursive React component. Given a `LayoutNode`:

- If **leaf** → render `<Slot />`
- If **split** → render two panes sized by `ratio`, with a `<ResizeHandle />` between them

Pane sizes are set via `flexBasis`. Path breadcrumbs are threaded down to identify which `SplitNode` a resize handle belongs to.

---

## Slot UI

Each slot has a toolbar and a content area.

Toolbar controls:
- `⠿` — drag handle (makes the slot draggable for swapping)
- `H` / `V` — split this slot horizontally or vertically
- `✕` — remove this slot

Slots are both **draggable** (from their toolbar) and **drop targets**. Dropping one slot onto another calls `swap()`. A blue border and faded content indicate an active drop target.

## Current State & Known Issues

The core is working — split, remove, resize, and drag-to-swap all function. But there are rough edges:

- **Resize can feel imprecise.** The delta-to-ratio calculation works, but the behavior near nested splits can feel off.
- **No minimum slot size in pixels.** The ratio clamp (0.1–0.9) helps but doesn't guarantee a usable slot at small window sizes.
- **Drag-to-swap has no visual cue on the dragged item.** Only the drop target shows feedback; the dragging slot shows nothing.
- **StubWidget is a placeholder only.** `componentId` is a string on `LeafNode`, but there is no component registry or loader yet. This is intentional — it is the next major piece after the grid is solid.
- **No persistence.** Layout resets on page reload.
- **No touch support.** `ResizeHandle` uses `MouseEvent` only. Desktop-first, intentional for now.

---

## What Comes Next (Not Now)

Once the grid is right:

1. **Component contract** — a stable typed interface that any widget must conform to. Custom components (or agent-generated ones) plug into slots through this contract.
2. **Component registry** — a mechanism to load and render real components from `componentId`.
3. **Error isolation** — error boundaries per slot so one bad widget can't break the dashboard.
4. **Persistence** — serialize the layout tree to localStorage or a backend.
